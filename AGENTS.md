# Agent Instructions

## General

- When a bug was identified, always add a test to confirm the issue. Then fix the bug, and finally run the same test again to confirm that the issue is gone. Keep the test to ensure that the bug will not happen anymore.
- After implementing a feature, always run all tests to ensure that the feature din't introduce a bug.
- Before assuming that a test failure was preexisting, confirm it by stashing the changes and running the tests again in the original code.
- In case you introduced a bug, try to identify the issue by comparing with the previous working state. Based on that analysis, fix the issue on the new code.
- Instead of assuming something when the task is unclear, ask the user.
- When making an architectural decision, always ask the user first with all possible options.
- When asked to find the issue of a failing test, do not simplify the test itself without the users consent.
- As soon as you have implemented a feature and all tests pass, commit it. Use a simple one-sentence commit message.
- After finishing the implementation, review the code from a separate subagent that only knows the plan but not the actual implementation. The subagent should review the code (cleanliness, code duplication, potential bugs or missing implementation details, run clippy lints, removed or changed tests ...) and provide feedback to the main agent.
- Do not use emojis.

## Project-specific

- When running tests, use `cargo test --release` such that they are faster. Also make sure to save the entire output to a log file to avoid needing to re-run the tests if output information is required. Do NOT run tests if you only modified the app/cli wrappers.
- Before reading XFA semantics into a tool or prompt, consult the [XFA specs](./specs/XFA-3_3.txt) (text extraction of `specs/XFA-3_3.pdf`).
- Tests should never work with the output files. Instead they should analyze the documents and intermediate structures directly.
- The conversion is AI-guided end to end: a run authors one JSON document in its target's UBS format (`UbsAemDocument` or `UbsRedactoDocument`) with the `json_*` tools, and the vendored UBS layers (`u2s/crates/u2s-aem-ubs-mcp`, `u2s/crates/u2s-redacto-ubs-mcp`) encode it. There is no deterministic conversion to fall back on. The UBS writer, its templates (`profiles/ubs/aem`), the normalize passes, the XSD and the Redacto furniture live in those crates upstream, in `ajila-forms-conversion-engine-v3`: change them there and re-sync, never here. AEM output belongs in the templates as much as possible.
- The AEM output is judged by the feedback repo's CI guard, because a converted form joins the
  corpus that guard polices. Run it on a package a conversion wrote with
  `python3 scripts/check_feedback_rules.py <package.zip> forms/AAOS_033_IT.pdf` (it needs
  `../ajila-forms-conversion-feedback`); every enrolled rule must be clean, bar the two exceptions below. The rules themselves are
  in `specs/feedback/consistent-problems.md`, and the shapes a person still applies by hand in
  `specs/feedback/manual-changes-italy-033.md`. The ones a document can break are also checked on
  every edit, as the UBS rules in `u2s-aem-ubs-mcp/rules/` (`rule_check`); the rest the templates
  guarantee, and the parity tests upstream hold the encoder to the retired engine's output.
- Three of those rules are about a node's position among its siblings, so no template can satisfy
  them: they live in the UBS layer's `normalize.rs` and run over a copy of the tree on the way into
  the writer, which is what makes them hold for an agent-authored or loaded document as well.
- Where a node shows up is `AemAttrs` on the node, not a template guess: `summary_exclude` is what
  keeps content out of the UBS DoR (Redacto renders it from the summary), `dor_exclude` is Adobe's
  own switch, and `always_in_pdf` is how a hidden node still reaches the printed document.
- Partner and signature blocks follow the UBS general-fragments directive (specs/"AF Fragments and Common Fields with XSD List.md", 2026-08-20), and the document authors them from ordinary nodes: there are no custom elements. A party is a `Repeatable` wrapping one of the four `afforms_ubs_fragmentlib` partner generics, whose `init_hide` lists the sub-panels its one Initialize `hideAFHideDor` rule hides (only a partner generic takes it); its signature is a `Repeatable` wrapping `affrg_SignatureGeneric1`, both named after the party (`RCP_SGN_CPGRP`/`PN_SGN_CPGRP` for `PN_CPGRP`, `RCP_Sign_AHGRP`/`PN_Sign_AHGRP` for `PN_AHGRP`, `PN_SGN_BOGRP` and `PN_SGN_PAGRP` for the beneficial owner and the POA), and the UBS layer pairs the two by that name, so the party's Add and Remove drive both. The `ubs-aem-retired-market-fragments` and `ubs-aem-global-internal-bank-use` rules check every document; do not reintroduce germany/italy person or signature fragments.
- Two feedback-guard rules are accepted exceptions, by decision (2026-09-29): the signer-name fill (`PROBLEM-signature-name-fill`) is left to a person in AEM, and a party repeatable's Add label (`PROBLEM-repeatable-add-label`) may fail only on a form that ships no English: elsewhere the Author titles the repeatable in English with its translations, as the prompts explain, and a failure is a defect. Every other enrolled rule must be clean.
- The XSD is generated from the **AemNode** tree (the UBS layer's `xsd/from_aem.rs`), and each node's `bindRef` is assigned during that same walk, so a form's bindRefs are by construction exact element paths in its schema. Do not add a second XSD source. Customer-specific element names, ignore rules and occurrence overrides belong in the UBS layer's `profiles/ubs/xsd/config.toml` under `[[aemElements]]`, never in Rust.

## Layout

| Crate | What belongs there |
|---|---|
| `agent` | The headless conversion agent: the tool catalog and executor over the run's one output document (the `json_*` and `rule_*` tools from the vendored `u2s-doc-tools`, the builds through the UBS layers), the check rules and their sandbox (`rules.rs`), the edit-history store and session restore, the reference store with its semantic matcher, the embedded profile fonts, and the adapter over the vendored u2s tool servers (`u2s.rs`: source-form reads and renders, PDF viewing, and the Docker-hosted AEM and Redacto verifiers, all linked in-process). No UI and no LLM. |
| `pipeline` | The conversion controller: Analyst → Author → Reviewer sequencing, retry recovery, the stuck watchdog. Each stage runs as a real rig `Agent`, driven through `AgentRunner::stream()` (`run_stage`); `hooks::StageHook` reproduces the abort flag, the tool timeline, the stuck watchdog and the output-cap nudge, shapes a growing stage's history every turn through `memory::ContextBudget` (`on_completion_call` → `RequestPatch::history`), and reproduces the operator's retry prompt by restarting a fresh attempt from where a failed one left off. `memory::SqliteConversationMemory` is the `rig_core::memory::ConversationMemory` backend `build_stage_agent` attaches (wrapped in `rig_memory::CompactingMemory`) whenever a stage has a real session id, so a resumed session's Author/Reviewer loads its prior run's conversation. Reaches the outside world only through `SharedObserver` (progress) and the `ModelHandle`/`PriceFn`/`ContextBudget` the caller supplies via `RunConfig`, so it needs neither a UI framework nor a network to test — rig's own `MockCompletionModel` drives it instead. |
| `runner` | The host side of a run, shared by `app` and `cli`: the rig client factory (`client.rs`, the only place a provider is named), the per-endpoint request gate (`ratelimit.rs`) and model limits (`models.rs`), the calibrated `TokenCounter` and context budget (`token_counter.rs` — image vision-cost and the calibration EMA recovered from the old hand-rolled eviction ladder; deliberately not `rig_memory::HeuristicTokenCounter`, which flat-rates every image), the operator settings, `turns::TurnPlan` resolving an endpoint to what `pipeline` needs, and the entry points that build the agent, open a history session and record the result. |
| `app` | The Dioxus desktop app: the observer implementation and all UI state. |
| `mcp` | A stdio MCP server exposing `agent`'s tools to an external LLM client. |
| `cli` | `convert` (the AI conversion run headless, over `runner`), `sessions` and `verify`. |
| `u2s/` | Crates vendored from `ajila-forms-conversion-engine-v3`; see `u2s/VENDORED.md`. Never edit them in place: change them through a patch in `u2s/patches/`, and re-sync with `scripts/sync-u2s.sh <checkout>`. |

- A run produces one **output target** (`OutputTarget::Aem` or `Redacto`), each one UBS format. `profiles/<name>/` holds what a customer profile adds here: its source forms' fonts (`parser/fonts`) and, in `history.db`, its reference forms.
- Every edit to the document is recorded under the session's `#document` sibling in `history.db`, and a resumed run starts from the latest one. Sessions recorded before this (structured or `#aem` tree snapshots) stay listed but cannot be resumed.
- Rules run in a sandboxed worker process (`u2s_rules_host::worker`), which is the converting executable itself started with `--u2s-rules-worker`: the app, the CLI and the MCP server call `agent::rules::serve_worker_if_invoked()` first thing in `main`, and a new binary that converts must too. Test binaries cannot, so the agent tests use the standalone worker: build it with `cargo build -p u2s-rules-host --bin u2s-rules-worker` (`--release` for release builds) first. A run whose rules cannot run is refused, like one whose verifier is not ready.
- Tools are scoped **once**, in `SCOPING` in `agent/src/conversion/catalog.rs`: each tool declares which targets may execute it and which pipeline stages are offered it. Do not add a second allow-list anywhere — add a row there. The u2s tools (`xfa_*`, `pdf_*`, `aem_verify_*`, `redacto_verify_*`) are ordinary rows too: their specs come from the vendored crates through `agent/src/u2s.rs`, which also renames the two verifier families (both call their tools `verify_*` upstream) and removes the arguments it supplies itself (the artifact, the session).
- Verification is not optional. Every run checks its target's verifier first (`agent::u2s::aem_verify_readiness` / `redacto_verify_readiness`: settings, Docker, the images, the AEM data volume, pdfium) and refuses to start when it is not ready; do not add a switch or a silent fallback. The AEM verifier boots ajila's private AEM Forms image (pulled after `az acr login`) on a Docker volume with the UBS platform baked in (`docker/aem/README.md`); only an ARM image exists, so AEM conversions currently run on Apple Silicon hosts only. The Redacto verifier boots a Redacto platform of the run's own from four images (`docker/redacto/README.md`): the public Postgres image and the platform's migration, core and rendering images from ajila's private registry (pulled after `az acr login --name ajilaclouddev`). Every exit path of a run tears the verifier's containers down (`ConversionAgent::shutdown_verifiers`), and an idle verifier is torn down after 30 minutes. All AEM verifier sessions share the one data volume, so only one conversion at a time, across the app, the CLI and the MCP server, may drive it: an OS lock file next to `history.db` (`aem-verifier.lock`) enforces that, and leftover containers of a crashed run are removed only while holding it (Redacto uses a shared lock the same way).
- pdfium, which the `pdf_*` tools load, is pinned by release and checksum in `scripts/fetch-pdfium.sh`; run it before building or testing, and ship `libpdfium` next to a released binary.
- The agent reads the source form only through the u2s `xfa_*` tools: there are no engine-derived states, so a hidden section exists in the output only if a stage revealed it with `xfa_set`. The rules (`rule_check`) check the document on its own; source coverage is the stages' job, and the prompts say so.
- The source forms the tests and conversions use live in `forms/` (Git LFS).
- The tool catalog is pinned by `agent/tests/catalog.json`. After an intended change, regenerate with `UPDATE_SNAPSHOTS=1 cargo test -p agent` and review the diff: tool descriptions are prompt surface, so a wording change is a behaviour change.
- Tool descriptions and role prompts may only name tools that exist; `prose_only_names_tools_that_exist` enforces it. Prompt text lives in `agent/src/conversion/prompts.rs`.
- Run analysis: `pipeline` reports a structured `TraceEvent` stream through `RunObserver::trace` (default no-op) — durations measured there, full content, no wall clock; `runner::analysis` records it into a per-run folder (`report.md`, `timeline.md`, `transcript/`, `trace.jsonl`, `summary.json`, and the `evaluation.md` template for the human evaluation) under `run-analysis/` in the checkout by default by wrapping the caller's observer in `run::drive`. A new controller decision worth analysing gets a `ControlKind`, not a free-text `Thought`. The files are for people and AI assistants alike: keep them plain Markdown/JSONL, conclusions first, units on every number, `#seq` pointing back into `trace.jsonl`. Cross-run aggregation is `scripts/analyze_runs.py` over `summary.json` and `scripts/collect_evaluations.py` over the filled-in `evaluation.md` files (keep the template's front matter keys and table columns in step with it); bump `analysis::SCHEMA_VERSION` (and the script's `SUPPORTED_SCHEMA`) when either layout changes. See `docs/run-analysis.md`.
- Controller behaviour (stage order, retry, abort) belongs in `pipeline` and gets a test there — rig's own `MockCompletionModel` plus a recording `RunObserver` drive the real `run` with no network. Do not add sequencing logic to the app.
